# DTSC3602 Group 9 — D2 Data Note

Evan Smith · Andrew Wallace · Ikumi Uemura · Emmett Lashbrook · Brian Aguirre

D1 built a resume↔posting recommender on top of the raw LinkedIn postings and resume
datasets. This note is D2's data audit: what's actually in the data, what's wrong with
it, what we fixed versus documented, and what's now locked away as the final test set.
The full candidate-plot set and generated data dictionary live alongside the code (see
**Where to look** at the end); this note picks the plots that matter most for those two
questions.

## 1. Data sources

| `postings/postings.csv` | 123,849 | title, description, location, work type, salary, experience level |
| `postings/jobs/job_skills.csv`, `job_industries.csv` | 213,768 / 164,808 | taxonomy tags, joined by `job_id` |

## 2. Cleaning performed

Three issues were common enough, and clear-cut enough, to fix rather than just note.
Every fix is **additive** — new flag/indicator columns, nothing overwritten — so D1's
already-trained model (fit on the unflagged data) stays valid.

- **Salary outliers.** `postings.csv`'s `normalized_salary` ranges from \$0 to
  **\$535.6M**; `salaries.csv` separately has `max_salary` up to \$120M. These are
  data-entry/scale errors (e.g. an hourly rate keyed in as an annual figure), not real
  pay. `src/audit.py::flag_salary_outliers` flags anything outside a fixed
  \$1,000–\$1,000,000/yr sanity band — a fixed band, not a percentile cut, since a
  percentile would also clip legitimate high executive salaries. **438 of 36,069**
  salaried postings (1.2%) are flagged.
- **Sentinel values in `companies.csv`.** `state`, `zip_code`, `address`, and `country`
  use `"0"`, `"-"`, empty strings, or the non-ISO code `"OO"` as placeholders instead of
  a true null. A naive `isna()` check undercounts missingness by **9.0% (state) to
  16.3% (address)** of all 24,473 companies. `normalize_company_sentinels` replaces
  these with real `NaN` and keeps a `*_was_sentinel` flag per field.
- **Likely-duplicate postings.** **8,431 of 123,781** postings (6.8%) share
  `(title, company_name, location)` with another row under a different `job_id` —
  almost certainly re-posted listings. `flag_duplicate_postings` marks every row after
  the first in each group as `is_likely_duplicate` rather than dropping it: D1's model
  already trained on the undeduped corpus, and silently shrinking row counts now would
  move downstream metrics for a reason unrelated to this audit.

## 3. Known limitations — documented, not fixed

- **Encoding corruption.** 101 of 123,849 postings (`description`) and 6 of 2,484
  resumes (`Resume_str`) contain a literal U+FFFD replacement character — mojibake from
  a charset mismatch at the source. We flag but don't repair this: guessing which byte
  sequence a `�` replaced risks inventing text that was never actually written.
- **Orphaned foreign keys.** `job_skills.csv` and `job_industries.csv` each reference
  ~4,700 `job_id`s (about 3.7% of their rows) that don't exist in `postings.csv` at all.
  `data_load.py`'s existing joins already filter these out naturally before grouping, so
  no behavior changes — this is a property of the raw export, not a bug in our pipeline.
- **Unused raw sources.** `company_industries.csv`, `company_specialities.csv`, and most
  of `benefits.csv` (only 24% job-id coverage) are never joined into the model's feature
  set. Listed in the data dictionary so "we didn't look at this" is an explicit claim,
  not a silent gap.

## 4. Sampling concerns

- **Scrape sampling bias.** Both datasets are single LinkedIn-era snapshots, not a
  randomized sample of either the job market or the workforce — postings skew toward
  roles LinkedIn's scraper covers well (common white-collar titles), and the weak-label
  taxonomy inherits that skew (see the postings-per-category plot in
  `03_data_audit.ipynb`, §6).
- **Resume-category imbalance.** 24 categories range from 22 to 120 resumes each (~5×
  spread). Any category-level metric for the thin end (BPO, AUTOMOBILE, AGRICULTURE) is
  noisier than the headline numbers suggest.
- **Weak-label taxonomy proxy.** Carried over from D1 and restated here because it still
  governs every metric: fit labels come from a hand-authored taxonomy (title/skill/
  industry matching), not a hiring outcome. The model learns the taxonomy's notion of
  fit, not an employer's.

## 5. Reserved final test data

D1 already built a **doubly-disjoint** 80/20 split (`src/pairs.py::group_split`) —
resume IDs and job IDs are each partitioned independently, before any pair is drawn, so
no resume and no posting appears on both sides. Rather than carve a second, separate
holdout, D2 **freezes that existing test partition** as the project's reserved final
test set:

- **5,784 pairs · 496 resumes · 3,764 jobs**, label balance tracking the training split
  almost exactly (see `03_data_audit.ipynb`, §12 — no skew introduced by the partitioning
  itself).
- The freeze is enforced, not just claimed: `write ups/d2_test_split_freeze.json` holds a
  SHA256 fingerprint of the test resume/job ID sets. `python -m src.pairs --freeze-check`
  asserts the fingerprint still matches on every run — a changed seed, a changed
  `TEST_GROUP_FRAC`, or new data added to either raw file would trip this check before it
  silently invalidated the "reserved" claim.
- From this point forward, this partition is not touched again for model tuning or
  selection of any kind.
